# Senthuron Ops — Technical Architecture

**Companion to:** *Product Specification* and *UI/UX Design Specification*
**Stack:** Next.js (App Router) · TypeScript · PostgreSQL on Neon · Prisma · Tailwind CSS · Vercel
**Goal:** the smallest architecture that fully delivers the spec, and that one developer can explain end to end in a technical discussion.

> **Version note.** Conventions below (Prisma 7 with `prisma.config.ts` and driver adapters; Next.js 16 with async `searchParams`/`params` and `proxy.ts`) were checked against current documentation. After `npm install`, confirm them against the exact versions you get, and pin those versions in `package.json`.

---

## 0. Architecture at a glance

**One deployable app, one database.** There are no microservices, queues, caches, or separate backend.

```
                    ┌──────────────────────────── Vercel (one Next.js project) ───────────────────────────┐
                    │                                                                                    │
 Browser  ─────────►│  Server Components (pages)  ──┐                                                    │
 (React UI)         │                               ├──► Services (business rules) ──► Prisma ──► Neon   │
   │                │  Route Handlers  /api/*  ─────┘         ▲                                 Postgres │
   │  fetch()       │        ▲                                │                                          │
   └───────────────►│────────┘                     Zod schemas (shared validation)                      │
                    └────────────────────────────────────────────────────────────────────────────────────┘
```

**The three rules that hold the design together**

1. **Only services talk to Prisma.** Pages and route handlers never import the database client.
2. **One validation schema (Zod), used on both sides.** The same file validates the form in the browser and the request on the server.
3. **The URL is the state for anything you would want to share or refresh.** Search, filters, sort, page.

**Two doors into one service layer.** Server Components call services directly for reads. Route Handlers call the same services for the documented REST API and for all writes from the browser.

**What we deliberately do not use**

| Not used | Why |
|---|---|
| Microservices, queues, background jobs | No requirement needs them; follow-ups are dates, not scheduled notifications. |
| tRPC / GraphQL | REST route handlers are easier to demo and explain. |
| Redux / Zustand / React Query | Server Components plus the URL cover the state we have (§10). |
| Server Actions | We want an explicit, curl-testable API. Swapping later only replaces the thin handler layer. |
| Docker | Neon gives a hosted dev database in one click. |
| Auth library | Auth is out of scope (see §14 for the lightweight gate). |
| Monorepo, extra packages | One app, one `package.json`. |

## 2. Frontend architecture

### 2.1 Rendering model

| Concern | Decision |
|---|---|
| Router | Next.js App Router. |
| Default component type | **Server Component**. Add `"use client"` only for interactivity (forms, filter bar, dropdowns, dialogs, shortcuts). |
| Reads | Server Components call services directly. No self-HTTP calls. |
| Writes | Client components call `/api/*` with `fetch`, then `router.refresh()` or `router.push()`. |
| Caching | **None in v1.** Pages that read the database export `dynamic = "force-dynamic"` so they are never prerendered at build time. Route handlers respond with `Cache-Control: no-store`. |
| Styling | Tailwind CSS with the UI-spec tokens defined once in `globals.css` (`@theme` block on Tailwind v4, or `theme.extend` on v3). |
| Components | shadcn/ui primitives (Radix) restyled to the tokens; domain components built on top. |
| Icons / toasts / forms | Lucide · Sonner · React Hook Form with the Zod resolver. |

> **Gotcha worth remembering:** a Server Component page that only calls the database, with no dynamic input, may be treated as static and render *once at build time*. `force-dynamic` prevents that. This is a common deployment bug, and a good thing to mention in an interview.

### 2.2 Route map

| Route | Type | Data source | Notes |
|---|---|---|---|
| `/` | Server page | `dashboard.service` (per section) | Sections stream independently. |
| `/enquiries` | Server page | `enquiry.service.list(searchParams)` | Filters live in the URL. |
| `/enquiries/new` | Server page + client form | `team.service.list()` | Passes team members to the form. |
| `/enquiries/[id]` | Server page + client panel | `enquiry.service.get(id)` | `notFound()` if missing. |
| `/enquiries/[id]/edit` | Server page + client form | `get(id)` + team members | Same form component as create. |

### 2.3 Loading, empty, error, success (mapped to the UI spec)

| State | Mechanism |
|---|---|
| **Route loading** | `loading.tsx` per route renders skeletons that mirror the layout. Skeleton wrapper fades in after 150ms (CSS `animation-delay`). |
| **Section loading (dashboard)** | Each dashboard section is an async Server Component inside its own `<Suspense fallback={<SectionSkeleton/>}>`. |
| **Refetch on filter change** | `FilterBar` calls `router.replace(url)` inside `startTransition`; the pending flag dims the results (§10.3). |
| **Empty** | Components check `items.length === 0` and render `EmptyState` (variants: `none`, `filtered`, `dashboard`). |
| **Error (section)** | `SectionBoundary` (a small client error boundary) wraps list results and each dashboard section, rendering `ErrorPanel` with a **Try again** button that calls `router.refresh()`. |
| **Error (route)** | `error.tsx` in the `(app)` group; `not-found.tsx` for missing enquiries; `global-error.tsx` last resort. |
| **Success** | `toast.success()` (Sonner) before navigating; inline "Saved" for quick actions; activity highlight on the detail page. |

### 2.4 Data-fetching sequence: reading the list

```
Browser        Next.js server (page.tsx)          enquiry.service               Neon
  │ GET /enquiries?status=QUALIFIED&q=acme
  ├──────────────►│ await searchParams
  │               │ parseListQuery(searchParams)  (Zod → typed query, safe defaults)
  │               ├────────────────────────────►│ buildWhere(query)
  │               │                              ├── count, findMany, groupBy (Promise.all) ──►│
  │               │◄─────────────────────────────┤ { items, total, statusCounts, … }
  │◄──────────────┤ streamed HTML (server-rendered table)
```

### 2.5 Data-fetching sequence: creating an enquiry

```
Browser (EnquiryForm)             /api/enquiries (route.ts)         enquiry.service             Neon
  │ validate with Zod (client)
  │ POST JSON ───────────────────►│ assertSameOrigin, parse JSON
  │                               │ createEnquirySchema.parse (server = source of truth)
  │                               ├────────────────────────────────►│ create + CREATED activity (transaction) ─►│
  │◄──────────────────────────────┤ 201 { data: EnquiryDTO }
  │ toast.success("Enquiry created")
  │ router.push(`/enquiries/${id}`)   → detail page renders fresh from the database
```

## 3. Backend / API architecture

### 3.1 Layers

```
Route Handler / Server Component        ← thin: parse input, call service, shape output
        │
      Service                           ← business rules, database access, activity logging
        │
      Prisma Client                     ← only imported inside services and db.ts
```

| Layer | Responsibilities | Must not |
|---|---|---|
| **Route handler** | Read JSON/query, run Zod, call one service function, return `{data}` or `{error}` | Contain business rules or Prisma calls |
| **Service** | Build queries, enforce rules (Won/Lost clears follow-up), write activity in a transaction, map to DTOs | Know about HTTP or React |
| **Mapper** | Convert Prisma rows to DTOs; compute `reference` and `followUpState` | Query the database |
| **Validation** | Define what a valid request looks like | Talk to the database |

### 3.2 Business rules (all live in `enquiry.service.ts`)

| Rule | Behaviour |
|---|---|
| Create | Insert enquiry, derive `phoneDigits`, write a `CREATED` activity. If status is Won/Lost, `nextFollowUpAt` is stored as null. |
| Status change | Update status, write `STATUS_CHANGED` with `fromValue`/`toValue` (enum keys). If new status is Won/Lost, set follow-up to null. If `closingNote` is provided, store it in the activity `note`. |
| Assignee change | Write `ASSIGNEE_CHANGED` with names (or `null` for unassigned). Assignee must exist. |
| Follow-up change | Write `FOLLOW_UP_CHANGED` with ISO dates. Past dates allowed on update, not on create. |
| Other detail edits | Write one `DETAILS_UPDATED` entry listing changed field names (e.g. `description, budget`). |
| Atomicity | The update and its activity rows are written in a single `prisma.$transaction`. |
| Concurrency | Last write wins; `updatedAt` is returned so the UI can show staleness. |
| No delete | There is no delete service or endpoint. |

### 3.3 Date handling (small but important)

- `nextFollowUpAt` is a **date-only** column (`@db.Date`). The API represents it as a string `"YYYY-MM-DD"`, never a timestamp.
- "Today" is computed once in `lib/dates.ts` using the business timezone constant (`Intl.DateTimeFormat` with `en-CA` and `timeZone`), then converted to a UTC-midnight `Date` for queries.
- The server computes `followUpState` (`OVERDUE | TODAY | UPCOMING | NONE | CLOSED`) and `followUpDays` (negative when overdue) for every enquiry DTO, so the UI never does timezone math.

### 3.4 Search and filtering implementation

- `buildWhere(query)` returns a Prisma `where` object combining conditions with AND.
- **Search (`q`):** case-insensitive `contains` across `clientName`, `contactPerson`, `email`, `description`, and `phoneDigits` (the last only when the query has ≥ 3 digits, matched against the digits-only form of `q`).
- **Filters:** `status` (enum, or `OPEN` meaning the five non-closed stages), `source`, `assignee` (id or `UNASSIGNED`), `due` (`ANY`, `OVERDUE`, `TODAY`, `NEXT7`, `NONE`).
- **Sort:** `followup` (default; soonest first, nulls last), `updated`, `newest`, `budget`. Always add a stable tie-breaker (`id`).
- **Status counts:** the same `where` *without* the status filter, grouped by status, so the strip's numbers match what a click would show.
- At the expected volume (hundreds of rows) plain `ILIKE` plus the indexes in §4 is enough; no full-text search extension is needed.

## 4. Database architecture

- **PostgreSQL on Neon** (serverless Postgres). One project, two branches: `main` (production) and `dev` (local and previews).
- **Two connection strings** (see §13):
  - `DATABASE_URL` — the **pooled** string (host contains `-pooler`). Used at runtime by the app.
  - `DIRECT_URL` — the **direct** string. Used only by the Prisma CLI for migrations and seeding.
- **Access:** Prisma 7 with the `@prisma/adapter-pg` driver adapter on the standard Node.js runtime. Serverless functions are short-lived, so a small connection pool per instance (for example max 5) is enough because Neon's pooler does the heavy lifting.
- **Migrations:** Prisma Migrate. Commit `prisma/migrations/`.
- **Money:** `budget` is an `Int` in whole currency units (avoids Decimal serialisation issues; max 999,999,999 fits an Int).
- **Time:** timestamps are `timestamptz` via Prisma `DateTime`; the follow-up is a `date`.
- **Cold starts:** on Neon's free tier the compute can suspend when idle, so the first request after a pause may be slower. The skeleton states cover it; open the app once before a demo to warm it.

**Indexes**

| Table | Index | Serves |
|---|---|---|
| `enquiries` | `status` | Status filter, stage counts |
| `enquiries` | `source` | Source filter, source chart |
| `enquiries` | `assignedToId` | Assignee filter, workload |
| `enquiries` | `nextFollowUpAt` | Overdue/due queries, default sort |
| `enquiries` | `updatedAt` | "Recently updated" sort |
| `enquiries` | `(status, nextFollowUpAt)` | "Needs attention" query |
| `enquiry_activities` | `(enquiryId, createdAt)` | Activity timeline |
| `enquiry_activities` | `createdAt` | Dashboard recent activity |

## 5. Prisma models

Prisma 7 keeps the connection URL in `prisma.config.ts`, so the `datasource` block only names the provider.

```prisma
// prisma/schema.prisma

generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}

enum EnquiryStatus {
  NEW
  CONTACTED
  QUALIFIED
  PROPOSAL_SENT
  NEGOTIATION
  WON
  LOST
}

enum EnquirySource {
  WHATSAPP
  INSTAGRAM
  EMAIL
  WEBSITE
  REFERRAL
  DIRECT
  OTHER
}

enum ServiceType {
  WEB_DEVELOPMENT
  MOBILE_APP
  UI_UX_DESIGN
  CUSTOM_SOFTWARE
  MAINTENANCE_SUPPORT
  CONSULTING
  OTHER
}

enum ActivityType {
  CREATED
  STATUS_CHANGED
  FOLLOW_UP_CHANGED
  ASSIGNEE_CHANGED
  DETAILS_UPDATED
}

model TeamMember {
  id        String    @id @default(cuid())
  name      String    @unique
  email     String?
  createdAt DateTime  @default(now())
  enquiries Enquiry[]

  @@map("team_members")
}

model Enquiry {
  id             String        @id @default(cuid())
  number         Int           @unique @default(autoincrement())  // shown as ENQ-0042

  clientName     String
  contactPerson  String
  email          String?
  phone          String?
  phoneDigits    String?       // digits only, derived on write, used for phone search

  source         EnquirySource
  service        ServiceType
  description    String
  budget         Int?          // whole currency units

  status         EnquiryStatus @default(NEW)
  assignedToId   String?
  assignedTo     TeamMember?   @relation(fields: [assignedToId], references: [id], onDelete: SetNull)
  nextFollowUpAt DateTime?     @db.Date
  notes          String?

  createdAt      DateTime      @default(now())
  updatedAt      DateTime      @updatedAt

  activities     EnquiryActivity[]

  @@index([status])
  @@index([source])
  @@index([assignedToId])
  @@index([nextFollowUpAt])
  @@index([updatedAt])
  @@index([status, nextFollowUpAt])
  @@map("enquiries")
}

model EnquiryActivity {
  id         String       @id @default(cuid())
  enquiryId  String
  enquiry    Enquiry      @relation(fields: [enquiryId], references: [id], onDelete: Cascade)
  type       ActivityType
  fromValue  String?      // machine value: enum key, ISO date, or name
  toValue    String?
  note       String?      // e.g. closing note, or changed field names
  createdAt  DateTime     @default(now())

  @@index([enquiryId, createdAt])
  @@index([createdAt])
  @@map("enquiry_activities")
}
```

**Deviation from the product spec:** one derived column, `phoneDigits`, was added so phone search works regardless of how the number was typed (`+91 98765-43210` vs `9876543210`). It is filled by the service on create and update.

**CLI configuration**

```ts
// prisma.config.ts  (reference sketch)
import "dotenv/config";
import { defineConfig, env } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: { path: "prisma/migrations", seed: "tsx prisma/seed.ts" },
  datasource: { url: env("DIRECT_URL") },   // CLI uses the direct connection
});
```

**Runtime client (singleton, pooled URL)**

```ts
// src/lib/db.ts  (reference sketch)
import "server-only";
import { PrismaClient } from "@/generated/prisma/client";
import { PrismaPg } from "@prisma/adapter-pg";
import { env } from "@/lib/env";

const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient };

function createClient() {
  const adapter = new PrismaPg({ connectionString: env.DATABASE_URL });
  return new PrismaClient({ adapter });
}

export const prisma = globalForPrisma.prisma ?? createClient();
if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma;
```

The singleton stops development hot-reloads from opening a new connection pool every time. `server-only` makes the build fail if this file is ever imported into client code.

**Seed data.** `seed.ts` creates 5 fictional team members and about 30 enquiries covering every status and source. Follow-up dates are computed *relative to today* (for example: 3 overdue, 2 due today, several upcoming, a few unset) so the dashboard always looks alive. The seed clears existing rows first, so it refuses to run unless a `--reset` flag is passed, and it is never run automatically in production.

## 6. API routes

Base path `/api`. JSON in and out. Every response has `Cache-Control: no-store`.

| Method & path | Purpose | Success |
|---|---|---|
| `GET /api/enquiries` | List with search, filters, sort, pagination, status counts | 200 |
| `POST /api/enquiries` | Create an enquiry | 201 |
| `GET /api/enquiries/:id` | One enquiry with its activity | 200 |
| `PATCH /api/enquiries/:id` | Partial update (any subset of fields) | 200 |
| `GET /api/dashboard` | All dashboard aggregates | 200 |
| `GET /api/team-members` | Team members for selects and filters | 200 |
| `GET /api/health` | Database reachability check (`teamMember.count`) | 200 |

There is deliberately no `DELETE`.

### 6.1 List query parameters

| Param | Values | Default |
|---|---|---|
| `q` | string, ≤ 100 chars | — |
| `status` | `NEW … LOST` or `OPEN` | all |
| `source` | any `EnquirySource` | all |
| `assignee` | team member id or `UNASSIGNED` | all |
| `due` | `ANY`, `OVERDUE`, `TODAY`, `NEXT7`, `NONE` | `ANY` |
| `sort` | `followup`, `updated`, `newest`, `budget` | `followup` |
| `page` | integer ≥ 1 | 1 |
| `pageSize` | integer 1–50 | 15 |

Invalid or unknown query values fall back to their defaults for the **page** (so a hand-edited URL never crashes the UI) and return `400` from the **API**.

### 7.1 Envelopes

```jsonc

// error
{
  "error": {
    "code": "VALIDATION_ERROR",
```

| HTTP | `error.code` | When |
|---|---|---|
| 400 | `BAD_REQUEST` | Malformed JSON, invalid query parameters |

| 422 | `VALIDATION_ERROR` | Body fails the Zod schema or a business rule |

## 8. Validation strategy

**Principle: one schema, two enforcement points, server is the authority.**

| Where | Tool | Purpose |
|---|---|---|
| Browser | React Hook Form + Zod resolver | Instant, friendly feedback (on blur, then on change) |
| Server (route handler) | Same Zod schema | Trust boundary; rejects anything the browser missed |
| Server (service) | Business rules | Rules that need existing data (merged contact rule, Won/Lost clears follow-up) |
| Database | Prisma types, enums, FK, NOT NULL | Last line of defence |

### 8.1 Schema files

`src/lib/validation/enquiry.ts` exports:

- `enquiryFieldsSchema` — the base object with every field rule.
- `createEnquirySchema` — base + "follow-up not in the past" + "email or phone required".
- `updateEnquirySchema` — every field optional; the service merges the patch with the current record and re-checks the "email or phone required" rule on the **merged** result.
- `listQuerySchema` — coerces and defaults URL/query params.
- Types (`CreateEnquiryInput`, `UpdateEnquiryInput`, `ListQuery`) come from `z.infer`, so there are no hand-written duplicates.

### 8.2 Field rules

| Field | Rule |
|---|---|
| `clientName` | trim, 2–120 chars |
| `contactPerson` | trim, 2–100 chars |
| `email` | optional; valid email; ≤ 254; empty string → `null` |
| `phone` | optional; only digits, spaces, `+`, `-`, `(`, `)`; 7–15 digits; empty → `null` |
| email/phone | at least one present (`superRefine` on the object) |
| `source`, `service`, `status` | must be a member of the Prisma enum (Zod `nativeEnum` / `enum` built from `constants.ts` so the lists cannot drift) |
| `description` | trim, 10–2000 chars |
| `budget` | optional; integer 0–999,999,999; empty → `null` |
| `assignedToId` | optional `cuid` string or `null`; existence checked in the service |
| `nextFollowUpAt` | optional `YYYY-MM-DD` that is a real calendar date, or `null`; not before today on **create** only |
| `notes` | optional; ≤ 2000; empty → `null` |
| `closingNote` (PATCH only) | optional; ≤ 500; only valid together with `status` |

### 8.3 Error mapping

Zod's `error.flatten().fieldErrors` becomes the `fieldErrors` object in the 422 response. `EnquiryForm` feeds it to React Hook Form with `setError(field, { message })`, focuses the first invalid field, and shows the error summary (UI spec §6.8 D).

## 9. Error-handling strategy

### 9.1 Server

- `src/lib/errors.ts` defines `AppError(code, status, message, fieldErrors?)` with subclasses `BadRequestError`, `NotFoundError`, `ValidationError`, `ForbiddenOriginError`.
- **Services throw** typed errors (`NotFoundError` when an enquiry is missing, `ValidationError` for rule breaches such as an unknown assignee).
- `withErrorHandling(handler)` wraps every route handler and converts errors into the standard envelope:
  - `ZodError` → 422 with `fieldErrors`
  - `AppError` → its own status/code
  - Prisma known errors: `P2025` (record not found) → 404, `P2003` (foreign key) → 422
  - anything else → log the details server-side with a `requestId`, return a generic 500 message
- Server logs are structured (`console.error(JSON…)`) and appear in Vercel logs. Never log request bodies or personal data.
- Server Components: services throw; `notFound()` is used for missing records; the nearest `error.tsx` catches the rest.

### 9.2 Client

- `api-client.ts` returns a **discriminated result** and never throws for API errors:
  `{ ok: true, data }` or `{ ok: false, error: { code, message, fieldErrors? } }`.
  A network failure is converted into `{ ok: false, error: { code: "NETWORK_ERROR", … } }`.
- Every UI path reads that result and decides the surface:

| Error | UI surface (UI spec §6.8) |
|---|---|
| `VALIDATION_ERROR` on a form | Field errors + error summary, focus first invalid field |
| `NETWORK_ERROR` / `INTERNAL_ERROR` on submit | Alert above form, all input preserved, button re-enabled |
| Any error on a quick action | Revert value, inline message, error toast |
| Read failure in a Server Component | `SectionBoundary` → `ErrorPanel` with **Try again** |
| `NOT_FOUND` on detail | `not-found.tsx` |
| Unexpected render error | `error.tsx`, then `global-error.tsx` |

## 10. State-management approach

**No global state library.** Each kind of state has one obvious home:

| State | Home | Why |
|---|---|---|
| Search, filters, sort, page | **URL search params** | Shareable, refresh-safe, back button works, server can read it |
| Enquiry / dashboard data | **Server Components** (props) | Always fresh; no client cache to invalidate |
| Form values and errors | **React Hook Form** | Purpose-built for forms; pairs with Zod |
| Quick-action values (status, assignee, follow-up) | `useState` inside `HandlingPanel` | Small, local, optimistic |
| List "pending" flag (dimming) | `useTransition` + a small React context in `ListShell` | Filter bar and results need to share it |
| Dialog open/closed | local `useState` | Not shared |
| Toasts | **Sonner** (global `<Toaster/>`) | Survives navigation |
| Single-key shortcuts on/off | `localStorage` via `useKeyboardShortcuts` | Per-browser preference |

### 10.1 Filters in the URL

`FilterBar` builds a new `URLSearchParams` from the current one, resets `page`, and calls `router.replace(pathname + "?" + params)` inside `startTransition`. The server re-renders the list for the new params. Search input is debounced 300ms.

### 10.2 Mutations

After a successful write, the client calls `router.refresh()` (stay on page) or `router.push()` (navigate). Server Components re-run and pull fresh data, so there is nothing to sync manually.

### 10.3 Optimistic quick actions

1. `HandlingPanel` receives the enquiry as props and keeps the three controls in `useState`.
2. On change: update state immediately, send `PATCH`.
3. Success: show "Saved", then `router.refresh()`.
4. Failure: revert state, show the inline error and toast.
5. The panel is rendered with `key={enquiry.updatedAt}`, so when fresh props arrive it remounts with correct values instead of needing a sync effect.

### 10.4 List dimming

`ListShell` (client) wraps the toolbar and a `ResultsFrame`. `FilterBar` sets `isPending` from `useTransition`; `ResultsFrame` reads it from context and applies 60% opacity plus the progress line. The results themselves stay server-rendered and are passed as `children`.

## 12. Data-fetching approach

| Screen | Fetch method | Details |
|---|---|---|
| Dashboard | Server Component → `dashboard.service` functions | One function per section, run in parallel, streamed with `Suspense`. `React.cache()` de-duplicates the shared status-breakdown query within one request. |
| List | Server Component → `enquiry.service.list` | `count`, `findMany`, and `groupBy` run with `Promise.all`. |
| Detail | Server Component → `enquiry.service.get` | Missing → `notFound()`. |
| Create/Edit page | Server Component | Loads team members (and the enquiry for edit) and passes them as props. |
| Any write | Client `fetch` → `/api/*` | Then `router.refresh()` / `router.push()`. |
| External / scripted access | `/api/*` GET routes | Thin wrappers over the same services. |

**Dashboard queries (all through Prisma, no raw SQL)**

| Section | Query |
|---|---|
| Figures + stages | `groupBy status` (count and `_sum.budget`); overdue and due-today `count`; oldest overdue `findFirst` ordered by follow-up date |
| Needs attention | Three `findMany` calls (overdue, today, open with null follow-up) with `take` limits |
| Sources | `groupBy source` (all) and `groupBy source` where `status = WON` |
| Workload | `groupBy assignedToId` for open, and again for open + overdue; names from `team.service` |
| Recent activity | `enquiryActivity.findMany` ordered by `createdAt desc`, `take: 6`, selecting enquiry reference/name |

At hundreds of rows these are all fast with the indexes above. No caching layer is needed.

## 14. Security considerations

| Area | Measure |
|---|---|
| **Input** | Zod validation on every request; length limits; enum membership; `cuid` format check on ids; page size capped at 50. |
| **SQL injection** | Prisma parameterises everything; no raw SQL anywhere. |
| **XSS** | React escapes output; no `dangerouslySetInnerHTML`; `mailto:`, `tel:`, and `wa.me` links are built only from validated values (digits and validated email). |
| **Data exposure** | Mappers whitelist DTO fields; internal columns like `phoneDigits` never leave the server; 500 responses are generic and include only a `requestId`. |
| **CSRF / cross-origin writes** | Mutating routes require `Content-Type: application/json` and a matching `Origin`/`Host` (`assertSameOrigin`). This matters especially if the basic-auth gate is on, because browsers attach basic credentials automatically. |
| **Secrets** | Only in Vercel environment settings and local `.env`; never committed; no `NEXT_PUBLIC_` secrets. |
| **Server-only code** | `import "server-only"` in `db.ts`, `env.ts`, and services so the build fails if they are bundled for the browser. |
| **HTTP headers** | Set in `next.config.ts`: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Content-Security-Policy: frame-ancestors 'none'` (a full script CSP is skipped because Next.js inline scripts need nonces; noted as future work). |
| **Access control** | Authentication is out of scope (assumption A1). The deployed demo uses **fictional data only** and an **optional passphrase gate** in `proxy.ts` (basic-auth check against the two env variables, comparing with a constant-time check). Remove the variables to disable it. |
| **Logging** | Structured server logs with `requestId`; no personal data or request bodies. |
| **Dependencies** | Pin versions, run `npm audit` before submission. |
| **Database** | Neon connection over TLS; separate branches for dev and production; the seed script refuses to run without `--reset`. |

Explicit non-goals: rate limiting, audit logging beyond the activity history, role-based permissions.

## 15. Deployment architecture

```
 Developer ──git push──► GitHub ──► Vercel (build + host)
                                      │  Production: main branch  ─► Neon branch "main"
                                      │  Preview: pull requests   ─► Neon branch "dev"
                                      │
 Browser ─────────HTTPS───────────────┘
                     │
        Next.js (Node.js serverless functions + static assets on Vercel's CDN)
                     │  pooled connection (DATABASE_URL, -pooler host)
                     ▼
              Neon PostgreSQL  ◄── Prisma CLI (DIRECT_URL) for migrations & seed
```

**Steps**

1. Create a Neon project with two branches, `main` and `dev`. Copy the pooled and direct connection strings for each.
2. Create the Vercel project from the GitHub repository (Next.js preset). Set Node.js to a version supported by Prisma 7 (20.19+, 22.12+, or 24+).
3. Add `DATABASE_URL`, `DIRECT_URL` (and optional passphrase variables) to Vercel: *Production* → `main` branch values; *Preview* and *Development* → `dev` branch values.
4. Package scripts:
   - `postinstall`: `prisma generate`
   - `build`: `prisma generate && next build`
   - `vercel-build`: `prisma migrate deploy && next build` (migrations run on every deploy; requires `DIRECT_URL` at build time)
   - `db:migrate`: `prisma migrate dev`
   - `db:seed`: `prisma db seed -- --reset`
5. Set the Vercel function region to match the Neon region (fewer network hops per query).
6. **Deploy early** (Phase 0) with a placeholder page and `/api/health`, then deploy on every push. Never leave deployment to the last hour.
7. After the first production deploy, run the seed once against `main` from your machine (with production `DIRECT_URL` temporarily exported), or import the demo data from the dev branch.
8. Deployment checklist: `/api/health` returns 200; dashboard loads; create → view → edit flow works on the live URL; mobile widths checked on a real phone.

**Runtime notes**
- All server code runs on the Node.js runtime (not Edge), which keeps Prisma with the standard `pg` adapter simple.
- Static assets, fonts, and the JS bundle are served from Vercel's CDN automatically.
- There are no cron jobs, background workers, or file storage.

## 17. How to explain this in a technical discussion

### 17.1 The 60-second version

> "It's a single Next.js app on Vercel with a Neon Postgres database. Pages are Server Components that call a service layer directly for reads. Writes go through REST route handlers that call the same services. The services are the only code that uses Prisma, and one Zod schema validates both the form and the API request. Search and filters live in the URL, so they're shareable and survive a refresh. The database has three tables: enquiries, team members, and an activity log for status changes. I kept it deliberately simple: no extra state library, no microservices."

### 17.2 Key decisions and the reasoning

| Decision | Reason | Trade-off |
|---|---|---|
| Server Components for reads | Fewer moving parts, always-fresh data, no client cache | Interactions need `router.refresh()` |
| Route Handlers for writes | Explicit, testable API; easy to demo | Slightly more code than Server Actions |
| Service layer | Business rules in one place; both doors reuse it | An extra file per domain |
| Shared Zod schema | One definition of "valid"; types derived for free | Schema must stay free of server-only code |
| URL as state for filters | Shareable, refresh-safe, no state library | Every change triggers a server render |
| Date-only follow-up + server-computed state | Avoids timezone bugs | One helper module to maintain |
| Activity table | Real "lifecycle tracking" with history | Extra writes in a transaction |
| Neon pooled + direct URLs | Serverless-friendly runtime; migrations need a direct connection | Two variables to configure |
| No auth | Out of the brief; keeps scope honest | Public demo must use fake data and an optional gate |

### 17.3 Questions you should be ready for

| Question | Short answer |
|---|---|
| Why not call the API from server components? | It would be an extra network hop to ourselves. Sharing the service is faster and simpler. |
| Why both API GET routes and server reads? | The GET routes are thin wrappers that document and expose the same service; they cost almost nothing and help testing. |
| How do you prevent invalid data? | Client Zod for UX, server Zod for trust, business rules in the service, DB constraints as a backstop. |
| What happens if two people edit at once? | Last write wins; `updatedAt` is shown, and activity records every change. I would add optimistic locking with a version column next. |
| How does search perform at scale? | `ILIKE` with indexes is fine for hundreds of rows. For more I would add `pg_trgm` or full-text search. |
| Why is `budget` an integer? | Avoids decimal serialisation issues; the brief has no need for fractions. |
| How would you add authentication? | Add an auth library and a `userId` on activity; the `proxy.ts` gate and service layer are the natural hooks. |
| How would you add email reminders? | A scheduled job (Vercel Cron) calling a service function that finds due follow-ups. |
| What would you improve with more time? | Auth and roles, optimistic locking, full-text search, integration tests, CSV export. |
| What can go wrong on Vercel + Neon? | Static prerendering of DB pages (solved with `force-dynamic`), connection exhaustion (pooled URL + singleton), cold starts (skeletons, warm-up). |
